# Release process

one-fetch ships source and GitHub Release artifacts, never npm packages. A CI
artifact is for review only. It is not a deployment, Git tag, GitHub Release, or
xPanel update.

## Channels

- **0.1 Preview:** protocol and adapters can change with documented migration.
  Capabilities must state incomplete or degraded behavior truthfully.
- **1.0:** only after all three adapters pass real-environment conformance,
  backup/restore, security, audit, and version-mismatch gates.

Changesets update private workspace versions and release notes. They do not
publish, tag, deploy, or create a Release.

## Required artifacts

For version `<version>`, the review bundle contains:

- `one-fetch-protocol-<version>.tgz`;
- `one-fetch-core-<version>.tgz` (client runtime dependency);
- `one-fetch-client-<version>.tgz`;
- `one-fetch-types-<version>.tgz`;
- `one-fetch-node-<version>.tar.gz` (portable ESM runtime and production dependencies);
- `one-fetch-node-<version>.Dockerfile`;
- `one-fetch-node-<version>.Dockerfile.dockerignore` (minimal OCI build context);
- `one-fetch-node-deploy-<version>.mjs` (versioned install/update/verify helper);
- `one-fetch-node-oci-<version>.json` (archive, Dockerfile, base-image and build metadata);
- `one-fetch-node-<version>.oci.tar` (unpublished `linux/amd64` and `linux/arm64` OCI image layout);
- `one-fetch-admin-<version>.zip` (self-hosted static management site);
- `one-fetch-protocol-schemas-<version>.json`;
- `one-fetch-control-openapi-<version>.json`;
- `one-fetch-release-manifest-<version>.json`;
- `one-fetch-sbom-<version>.cdx.json` generated by Syft;
- `one-fetch-node-oci-<version>.cdx.json` generated by Syft from the OCI archive;
- `SHA256SUMS` and `SHA512SUMS`;
- GitHub artifact provenance associated with every checksummed subject.

Package manifests use immutable GitHub Release URLs for private workspace
dependencies. Consumers lock those URLs and SHA-512 integrity; no package is
resolved from an unpublished npm name.

## Pull request gate

1. Add a Changeset describing protocol, capability, persistence, privacy, or
   operations impact.
2. Verify source files stay below the 1,000-line hard limit and normally below
   500 lines. Generated runtime declarations are excluded and reviewed by diff.
3. Run formatting, typecheck, unit/property tests, builds, adapter startup/dry
   runs, Admin tests, and conformance fixtures.
4. Run CodeQL, Gitleaks, the frozen-lockfile OSV audit, AST import-boundary
   checks, dependency policy, generated-file clean diff, and SBOM generation.
5. Review protocol/OpenAPI/JSON Schema changes and migration checksums.

PR jobs have read-only repository permissions and no provider deployment
credentials.

## Preview artifact gate

The manual `Release review bundle` workflow accepts a version and channel. It
must run from a reviewed commit on `main`, builds with the frozen lockfile,
generates checksums/SBOM/provenance, and uploads a workflow artifact. It does not
create a tag or Release.

Download the bundle and verify:

```bash
sha256sum --check SHA256SUMS
sha512sum --check SHA512SUMS
gh attestation verify --repo OKFred/one-fetch <artifact>
```

Use platform-equivalent checksum tools on Windows. Verify the manifest commit,
version, protocol version, filenames, package dependency URLs, schemas, and
license before installing any archive.

## Real-environment acceptance

Use synthetic targets and an exact temporary environment on each platform:

- Node 24.20.0 and Node 26 test matrix, SQLite crash/recovery, DNS pinning,
  explicit proxy rejection, CA/client certificate, timing, and rejection of
  every unsupported tunnel before upstream connection.
- Cloudflare workerd tests plus a temporary real Control/Gateway/D1/DO stack,
  Service Binding, cancellation, limits, header mutation, and cleanup.
- Supabase local Docker plus a temporary hosted project/functions/PostgreSQL
  stack, RPC privileges, platform logging disclosure, and cleanup.

All run the same conformance fixtures: duplicate path/query/headers, binary and
multipart bodies, target 5xx, relay/provider failures, repeated `Set-Cookie`,
`Server-Timing`, redirects, 20 MiB and 20 MiB+1, timeout, cancellation, quota,
policy/body matching, audit canaries, and protocol forgery.

Each platform also performs backup/restore, forward migration, Control/Gateway
version mismatch, signing-key mismatch, storage/audit failure, and rollback
rehearsals. Record exact deployment IDs and delete temporary resources by exact
ID after acceptance.

## Promotion to 1.0

Before `1.0.0`, require:

- complete passing evidence for every advertised capability on all adapters;
- no Preview-only synthetic success for unsupported alerts/backups/tunnels;
- signed audit export and offline verification, retention, daily seals, and
  Webhook retry/replay tests;
- successful encrypted backup and isolated restore per platform;
- protocol/client consumption by an xPanel test branch using fixed Release URLs
  and integrity hashes;
- clean repository and matching versions in all release manifests;
- SBOM, checksums, provenance, migration notes, privacy and permissions review.

After explicit approval, create an immutable annotated `v<version>` tag pointing
to the accepted `main` commit, then create the GitHub Release from the exact
reviewed bundle. Never move or reuse a tag. Verify the public Release assets and
attestations after publication.

Deployment of a stable instance, merging xPanel 3.0, generating its extension
package, and Chrome Web Store submission are independent approvals after the
one-fetch Release. No repository workflow combines these side effects.

## Public download verification

After publication, verify downloads without GitHub authentication:

```bash
pnpm release:verify-public --version 0.1.0 --commit 21e6b985f32e0dcfab5389dd7b2a77b89f72377b
```

This requires Node 24.20+ and system cURL 8.4+ with HTTPS support. It does not
read `GH_TOKEN`/`GITHUB_TOKEN`, `.netrc`, or `.curlrc`, and never uploads,
deploys, republishes, installs, or extracts the downloaded files. Standard
network proxy environment settings still apply. GitHub's
[public release asset API](https://docs.github.com/en/rest/releases/assets#get-a-release-asset)
supports unauthenticated access and exposes asset digests.

The verifier resolves the annotated tag to the explicit expected commit; it
does not trust the release's possibly moving `target_commitish` branch name.
It validates the channel, required artifact inventory, safe asset filenames,
canonical HTTPS download URLs, byte lengths, GitHub SHA-256 digests, manifest
identity, and published SHA-256/SHA-512 checksum lists. Artifact hashing is
streamed from disk, including the large OCI archive.

Downloads and unique JSON receipts default to `.tools/public-release/<version>/`.
An interrupted download stays in its asset-ID/SHA-256-specific `.part` file.
Rerunning the same command resumes it using
[cURL range continuation](https://curl.se/docs/manpage.html#-C).
By default, two assets download concurrently and each asset has up to three
300-second attempts. Transient network failures may retry; HTTP errors, unsafe
paths, unsupported range continuation, or digest mismatches stop that asset.
Use `--attempts 1..5` and `--timeout-seconds 1..3600` to tune the bounded retry
budget. `--output` must remain inside the checkout; choose a new ignored
directory for a completely fresh anonymous-download check.

Every finished run writes a new receipt, including partial failures. Successful
assets are retained when another asset fails. A reused file is rehashed and
reported as `verified-cache`, never as a new anonymous download. Nonzero exit
status and `state: incomplete` mean the gate has not passed. Do not execute a
partial file or treat it as an artifact. Corrupt files are preserved for
inspection, not silently overwritten; use a new output directory to retry.
Concurrent writers to the same asset are rejected. After an OS/process crash,
remove only its exact `download.lock` after confirming no verifier is active.
Use a private local output directory, not one writable by another account.

This check is **not provenance verification**: receipts explicitly record
`provenanceVerified: false`. Independently verify GitHub attestations against
the accepted source commit and release-review workflow as described above.
Download/cache receipts never replace adapter runtime, backup/restore, or
resource-cleanup acceptance evidence.
